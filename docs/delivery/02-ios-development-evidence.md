## QA visual y funcional local · iOS 26.5

La verificación operó la aplicación Release gratuita conectada a la API de desarrollo aislada `http://localhost:18080` y su base local `puntazo_ios_impl_20261101`. Se usaron cuentas sintéticas; no se escribieron datos en producción ni se desplegó el código. Fuentes identificadas: frontend `69ad97f445cb7c96d69686b7497ba72a77d41909` y backend `90cde5d29f86c8f16dfb91ab4273c48dd4f45dc4`. El informe seguro es `reports/ios-implementation-20261101/native-visual-qa.json`; preparación de fixture: `reports/ios-implementation-20261101/native-fixture-preparation.json`.

- Email login de comercio y cliente sintéticos; onboarding de comercio, selección de Sellos y primer beneficio sin pago. Las sesiones de cliente/comercio y iPad se restauraron tras cerrar y relanzar la app.
- Permiso de cámara denegado: el ingreso manual de código siguió disponible. La búsqueda del código sintético `CL-1` mostró vista previa y confirmó en UI la acumulación inicial de 0 a 1 sello.
- Para habilitar el premio de diez sellos, se prepararon nueve acumulaciones adicionales mediante llamadas legítimas a la API de preview/acumulación (sin SQL directo). El canje se revisó y confirmó desde la UI; el movimiento `CANJE` persistido fue consultado de forma independiente y dejó el saldo en cero. Un primer intento de fixture con clave de idempotencia inválida fue rechazado `422` antes de escribir.
- El selector de dirección mostró tiles de Google y el marker guardado; al cancelar volvió a la lista de sucursales. El mapa del cliente mostró los tiles y comercio/dirección correctos y seleccionó su tarjeta correspondiente. La ubicación se solicitó por acción del usuario: al denegarla, el mapa y catálogo siguieron utilizables con guía de permiso bloqueado. Se abrió Ajustes, se concedió “Al usar la app”, y al volver se actualizó el estado. Una coordenada simulada del Obelisco permitió recentrar, mostrar posición y distancia, y ordenar comercios cercanos.
- El permiso de biblioteca de fotos denegado devolvió al perfil; al reintentar, la interfaz mostró el aviso explícito para permitir acceso. No se seleccionaron ni subieron fotos.
- En iPad Pro 11-inch M4 con iPadOS 26.5 se inspeccionaron login y QR restaurado en retrato, y QR/navegación inferior en paisaje. Se reutilizó el mismo artefacto Release, sin recompilar específicamente para iPad.

La selección táctil y “Usar punto central” se probaron en el Release gratuito `3c5de42` y en la app interna con Metro `3c5de42`: el pin cambió y el PATCH `200` persistió coordenadas sintéticas nuevas en cada base local (gratis: `-34.601385, -58.431831`; interna: `-34.603709, -57.668253`); al reabrir el selector el pin se recuperó. Un intento anterior falló porque había ventanas duplicadas en DeviceHub; tras dejar una ventana, el tap funcionó, por lo que no se atribuye ese fallo al SDK de Google Maps. El gesto pinch no quedó verificado. En iPad Pro 11-inch M4/iPadOS 26.5, Release `3c5de42` preservó sesión sintética tras actualizar, mostró tarjeta/QR y tabs en retrato y paisaje, tiles/marker de tienda y ficha con retorno a la tarjeta; no fue regresión completa de comercio/scanner/media. Cámara física y selección/subida de fotos no se probaron (sólo denegación/fallback); Files abrió, pero no se completó subida, publicación ni render PDF. El export Android también pasó con límites de Maps descritos en la tabla. La compra/restauración Xcode se detalla abajo y no equivale a App Store/Sandbox. ## Compra local Xcode y recuperación JS · artefacto nativo 69ad97f

El binario nativo interno se había construido desde `69ad97f`; Metro sirvió primero el bundle JavaScript de `52eb49c` y, tras reload, el código de recuperación de `84829bc`. No se recompiló el artefacto nativo para esos cambios JS. Se resolvieron los paths de productos/intermedios de Xcode hacia el output CLI existente; el esquema local ignorado desactivó el attach del debugger que fallaba y `Run Without Building` lanzó la app mediante PosixSpawn. El bundle `billing-internal` conectó a la API local `http://localhost:18082`; se verificaron login local, consulta StoreKit, catálogo de Sellos y precios localizados. Backend `90cde5d` y base `puntazo_ios_native_ui_20261101` eran aislados, con cuentas sintéticas y sin correo ni writes de producción.

Con el trial de registro vigente, el catálogo seguía habilitado pero `eligible_to_purchase=false` y bloqueó iniciar una compra nueva. Una fixture local aislada envejecida habilitó elegibilidad al terminar el trial. Esto acredita la consulta/regla de elegibilidad local, no una compra comercial ni una transacción de App Store.

El primer intento obtuvo una intención autorizada, pero falló al construir las opciones antes de llamar `product.purchase`: OpenIAP 1.3.15 rechaza en modo Swift 5.9 cualquier valor no nulo para `introductoryOfferEligibilityOverrideIOS`; enviar `false` también activa esa rama. Por tanto, ese intento falló antes de iniciar una compra StoreKit. La reserva durable y el simulador original se preservaron; no se limpió SecureStore, ledger ni la operación. El fix `52eb49c` omitió el override opcional y pasó TypeScript + 28 pruebas dirigidas; el catálogo no ofrece introductorio Apple y el trial sigue gobernado por backend.

Con `52eb49c`, StoreKit Xcode presentó y confirmó la compra indicando que no había cargos reales. El primer `sync` backend respondió `400`: el certificado del JWS actual no coincidía con el pin de la fixture anterior. El JWS y certificado se verificaron offline; el pin se actualizó sólo en el entorno aislado Xcode, sin cambiar Production ni Sandbox. Tras reiniciar el runtime con JavaScript `84829bc`, la app recuperó de `Transaction.all` un JWS verificado que coincide con el transaction ID y producto exactos y lo validó contra la transacción original. La rutina de recuperación no registra ni expone el JWS, no sincroniza, no emite eventos y no finaliza la transacción; luego el flujo normal restauró esa transacción a la API local con `200` a las 12:50:27 ART. Las capturas JWS no eran byte por byte idénticas.

La restauración idempotente tras reload devolvió `200`; en ese momento el ledger mantuvo una transacción/cadena. OSLog independiente a las 12:57:28/12:57:39 ART registró lista pendiente vacía, `finishTransaction result: true` y lista vacía después. Luego, la compra directa de upgrade Sellos 1→2 para la misma marca/grupo mostró el sheet Xcode sin cargos reales: intención API `201` a las 13:13:42 ART, sync `200` a las 13:14:06.540 y `finishTransaction=true` a las 13:14:06.605 (65 ms tras el OK backend). La UI mostró capacidad 2 activa, una marca cubierta hasta el 1 de diciembre y gracia hasta el 8. El estado sintético final persistió dos transacciones de la misma cadena. Así queda verificado el finish de restore repetido y de la compra directa Xcode; el primer intento histórico que falló antes de `product.purchase` se conserva sólo como diagnóstico, no como recorrido exitoso. No es App Store, Sandbox ni servicios Apple reales.

`84829bc` añadió la recuperación JWS desde historial verificado para transacciones pending que llegan con ID sin JWS: exige ID y producto coincidentes, valida contra la compra original y no agrega un getter/log ni caminos de sincronización/finish dentro de la recuperación. TypeScript y 31 pruebas dirigidas pasaron en ese commit. El HEAD `3c5de42` añade el botón “Usar punto central” con `MapView.getCamera()` sin cambiar `react-native-maps`; QA posterior confirmó tap/centro y persistencia por API en bases aisladas. Evidencia: `reports/ios-implementation-20261101/storekit-purchase-options-fix-20261101.md`, `internal-metro-qa-52.json`, `internal-native-ui-failed-intent.json`, `internal-native-ui-purchase-observation.json`, `internal-native-ui-purchase-final.json`, `storekit-native-finish-observation.json`, `storekit-direct-purchase-observation.json`, `address-picker-free-release-persistence.json`, `address-picker-native-persistence.json`, `ipad-final-release-qa.json`, `android-final-regression.json` y `free-3c5de42-evidence.md`.

## Harness nativo StoreKit interno

Las nueve pruebas cubrieron veinte productos sin intro, compra con token de marca y finalización diferida, renovación, expiración, reembolso, Ask to Buy aprobado/declinado, restauración, y offer code de 50%/un mes sin `appAccountToken` seguido de renovación normal. Un intento anterior de ocho pruebas en runtime 26.5 falló con `SKInternalErrorDomain` 3; DTS confirmó la limitación en [Apple Developer Forums](https://developer.apple.com/forums/thread/826971), por lo que no se cuentan como aprobadas en ese runtime. Evidencia local: `/tmp/puntazo-ios-storekit262-v11.log` y `frontend/test-results/ios-storekit-native/StoreKit.xcresult`.

El primer artefacto gratuito usó `CODE_SIGNING_ALLOWED=NO` y falló al acceder a Keychain (-34018). El firmado ad hoc corrigió ese problema; el build final `69ad97f` terminó correctamente. El manifiesto de artefactos seguro está en `reports/ios-implementation-20261101/free-ios-native-audit.json`; su binario tiene SHA256 `9c50a13e77e6a67d9cc25b942305bb00276878ba4e2845588c26b003f89b2cb4`. El Release gratuito de `3c5de42` tiene evidencia de artefacto más reciente. Las pruebas `SKTestSession` y el API Xcode local no acreditan distribución, acceso Sandbox ni ejecución de App Store Server API. La QA Metro/Xcode confirmó compra directa de upgrade/restauración UI local, restore idempotente tras reload y finish independiente en OSLog tanto del restore repetido como de la compra directa. La validación directa/pinning del certificado Xcode está restringida al modo Xcode; Production y Sandbox mantienen validación estricta. No aceptar el certificado de pruebas para conceder derechos en esos entornos.
